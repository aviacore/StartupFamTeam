Как QA Engineer, я вижу свою задачу в том, чтобы обеспечить **надёжность, стабильность и предсказуемость** нашей AI-интеграции. Без качественного тестирования самый лучший API на бумаге превратится в источник головной боли в продакшене.

Моя экспертиза добавляет критически важный слой: **гарантию качества выходных данных и отказоустойчивость системы**. Я не просто выбираю API — я описываю, как проверить, что выбранное решение работает так, как ожидается, 24/7.

### Моя экспертиза (QA Engineer)

**Ключевые критерии с точки зрения обеспечения качества:**

1.  **Стабильность и консистентность ответов (Non-determinism):**
    *   **ChatGPT/OpenAI (GPT-4):** 8/10. При одинаковом промпте и настройках (`temperature=0`, `seed`) выдаёт наиболее стабильные результаты. Меньше всего «галлюцинаций» в структурированных данных (JSON, схемы). Легко писать регрессионные тесты.
    *   **Deepseek v.4:** 6/10. Заметно более «креативный» — при `temperature=0` всё равно может менять формулировки. Это усложняет автоматическую проверку эквивалентности ответов. Требует тестирования с допуском (fuzzy matching).
    *   **Gemini:** 5/10. Самый непредсказуемый. Может выдать правильную структуру, но с неверными данными внутри. Для QA — это кошмар: каждый тест нужно проверять вручную.
    *   **Бесплатные:** 2/10. Результаты могут меняться от запроса к запросу. Невозможно построить стабильный регрессионный набор тестов.

2.  **Возможность тестирования (Testability):**
    *   **ChatGPT/OpenAI (GPT-4):** 9/10.
        *   Чёткие коды ошибок (429, 400, 500).
        *   Возможность симулировать ответы через моки и стабы (mock/stub).
        *   Поддержка `seed` для детерминированных тестов.
        *   Есть песочница (Playground) для быстрой валидации промптов без написания кода.
    *   **Deepseek v.4:** 7/10. Меньше инструментов для отладки. Нет встроенного «seed». Тяжелее локализовать баги — часто «плавающие» ошибки.
    *   **Gemini:** 4/10. Неточные сообщения об ошибках. Сложно воспроизвести сценарий. Требуется много ручного тестирования.
    *   **Бесплатные:** 1/10. Невозможно протестировать заранее — всё узнаёшь в бою.

3.  **Производительность (Performance) и Latency:**
    *   **ChatGPT/OpenAI (GPT-4):** Стабильная задержка (latency) — 1-3 сек для типового запроса PM. Поддержка стриминга (streaming) для UX без задержек. Есть SLA.
    *   **Deepseek v.4:** Задержка может сильно варьироваться (от 0.5 сек до 10 сек) в зависимости от нагрузки. Нет строгого SLA. Для QA это означает необходимость тестирования таймаутов и ретраев.
    *   **Gemini:** Периодические «зависания» и высокая вариативность latency. Непредсказуемость — враг QA.
    *   **Бесплатные:** Часто rate-limited, могут отваливаться на 2-3 запросе. Непригодны для тестирования производительности.

4.  **E2E-тестирование и интеграция:**
    *   **ChatGPT/OpenAI (GPT-4):** Идеален для E2E. Чёткие ответы позволяют автоматизировать проверку связки `user action -> API call -> AI response -> UI update`.
    *   **Deepseek v.4:** Можно использовать для базовых E2E, но требуется больше допусков (assertions with tolerance).
    *   **Gemini:** Сломает любой E2E-тест своей непредсказуемостью. Придётся писать сложные обработчики исключений.

## Рекомендация QA Engineer (с точки зрения надёжности и тестируемости)

### Наилучший выбор: ChatGPT/OpenAI (платный)
- **Надёжность:** 9/10. Это, пожалуй, единственный API, на который можно положиться в production-среде. Стабильные ответы, понятные ошибки, предсказуемое поведение.
- **Тестируемость:** 9/10. Возможность использовать `seed` для детерминированных тестов — это **краеугольный камень** автоматизации QA. Мы можем написать регрессионные тесты, которые будут проверять:
  - Корректность структуры JSON (схема валидна).
  - Наличие обязательных полей (title, description, priority).
  - Логику fallback (если OpenAI не отвечает).
- **Performance:** Стабильная latency (1-3 сек) позволяет настроить адекватные таймауты. Стриминг снижает perceived latency (воспринимаемую задержку) для пользователя.
- **Мониторинг:** Встроенный дашборд OpenAI позволяет отслеживать количество ошибок. Можно быстро выявить регрессию.

### Альтернатива: Deepseek v.4
- **Надёжность:** 6/10. Хорош как fallback, но не для critical path (критического пути). Из-за нестабильности latency и «креативности» ответов, тесты будут часто «красными» (ложное срабатывание).
- **Тестируемость:** 6/10. Нужно будет писать тесты с плавающими ожиданиями (fuzzy matching). Например, проверять, что в ответе есть ключевые слова, а не точное совпадение. Это снижает качество проверки.
- **Рекомендация для QA:** Настроить мониторинг на ошибки Deepseek в production. Если частота ошибок падает (частота 5xx) превышает порог, нужно отправлять алерт в PagerDuty.

### Не рекомендуется: Gemini
- **Надёжность:** 4/10. Непредсказуемость — главный враг QA. Невозможно гарантировать, что завтра API будет работать так же, как сегодня.
- **Тестируемость:** 2/10. Практически невозможно написать стабильные автотесты. Каждый ручной тест-ран будет требовать «принятия решения» человеком.
- **Вердикт:** Использовать только для исследовательского тестирования (exploratory testing) новых сценариев, но не для регрессии.

### Бесплатные ключи – категорически не для QA
- **Причина:** Нулевая предсказуемость. Каждый запрос — сюрприз. QA превращается в угадайку.

### QA-стратегия для MVP (как тестировать)

#### 1. Unit-тесты (изоляция AI-клиента)
```typescript
// Используем моки для openai SDK
vi.mock('openai', () => {
  const mockCreate = vi.fn().mockResolvedValue({
    id: 'test-id',
    choices: [{ message: { content: JSON.stringify(mockResponse) } }],
  });
  // ... rest of mock
});
// Тест: Проверяем, что клиент возвращает правильную структуру
it('should return valid schema for PM task', async () => {
  const result = await aiClient.generateTask('Write spec for login page');
  expect(result).toHaveProperty('title');
  expect(result).toHaveProperty('acceptanceCriteria');
  expect(result).toHaveProperty('priority');
});
```

#### 2. E2E-тесты (интеграция AI в UI)
- **Сценарий:** Пользователь вводит описание задачи → нажимает «Сгенерировать спецификацию».
- **Шаги:**
  1. Открыть страницу «Новая задача».
  2. Ввести промпт: «Create task for implementing JWT auth».
  3. Нажать кнопку «Generate with AI».
  4. Подождать 5 секунд (пока стриминг завершится).
  5. Проверить: в поле «Заголовок» отображается текст, содержащий «JWT».
  6. Проверить: в поле «Описание» есть хотя бы 3 пункта.
  7. Проверить: кнопка «Сохранить» стала активной.
- **Провайдер для E2E:** Использовать **ChatGPT/OpenAI** для тестов, чтобы избежать ложных срабатываний.

#### 3. Performance-тестирование (нагрузка)
- **Цель:** Убедиться, что MVP выдерживает 10 одновременных запросов к AI без таймаутов.
- **Метрики:**
  - Среднее время ответа AI (p95 < 5 сек).
  - Количество ошибок 429 (rate limit) и 500 (server error).
  - Время обработки на стороне backend (должно быть < 100 мс без учёта AI).
- **Настройка:** Для performance-тестов использовать **Deepseek** как дешёвый и быстрый вариант, чтобы не тратить бюджет OpenAI.

#### 4. Тестирование Fallback-механизма (резильентность)
- **Сценарий:** OpenAI возвращает ошибку 429 (превышен лимит).
1. **Ожидание:** Backend автоматически переключается на Deepseek.
2. **Проверка:**
   - Ответ от Deepseek приходит в течение 10 секунд.
   - Структура ответа соответствует той же схеме, что и от OpenAI.
   - В логах появляется запись: `WARN: Primary client (OpenAI) failed, using Deepseek`.
3. **Инструмент:** Использовать `chaos-engineering` (например, искусственно заблокировать OpenAI на уровне сети).

### Итоговая рекомендация QA Engineer

**ChatGPT/OpenAI (платный) — это единственный вариант для создания предсказуемого и тестируемого продукта.**

- **Для PM:** Мы сможем автоматизировать проверку ваших требований. Никаких «вчера работало, сегодня нет».
- **Для CTO:** Fallback на Deepseek — это не просто «если OpenAI упадёт», а **тестируемый сценарий**, который мы можем прогнать в CI/CD.
- **Для Developer:** Предоставлю чёткие моки и тесты для AI-слоя. Вы будете уверены, что ваши изменения не сломают интеграцию.
- **Для CEO:** Качество — это не просто слово. Это стабильность работы MVP, которая напрямую влияет на удержание пользователей (retention).

**Единое мнение команды:** OpenAI как Primary, Deepseek как Fallback. **Категорически не использовать Gemini и бесплатные ключи для production.** QA-инфраструктура будет построена вокруг этого стека.
