# Plan_05 — Единый объединённый план

## Общая концепция

На основе анализа четырёх вариантов Plan_04 выделены ключевые общие элементы, которые легли в основу единого плана. Основная идея — создание системы, позволяющей ИИ-агентам эффективно координировать выполнение задач через асинхронный обмен сообщениями и централизованное управление приоритетами.

## Общие предложения (ядро плана)

1. **Архитектура на основе очередей задач**  
   Все четыре плана сходились на том, что для предотвращения конфликтов и дублирования работы необходима единая очередь, в которой каждая задача уникально идентифицируется. Агенты берут задачи по мере готовности, отмечая их статус (взято, выполняется, завершено).

2. **Механизм приоритизации**  
   Общим решением стало внедрение системы приоритетов (критический, высокий, средний, низкий). Приоритет влияет на порядок выдачи задач из очереди, но не блокирует выполнение менее важных задач, если они уже начаты.

3. **Асинхронный обмен отчётами**  
   Все версии предполагают, что каждый агент после выполнения задачи формирует структурированный отчет (в формате JSON) и отправляет его в общую директорию отчётов. Другие агенты могут подписываться на обновления.

4. **Единый контроллер-координатор**  
   Во всех планах присутствует модуль, который распределяет задачи, следит за временем выполнения и перезапускает «зависшие» задания. Координатор не выполняет задачи сам, а только управляет очередью.

5. **Логирование и аудит**  
   Каждое действие (взятие задачи, отчёт, ошибка) записывается в единый лог с временной меткой. Это позволяет анализировать производительность и откатывать изменения в случае сбоя.

## Структура единого плана (Plan_05)

### 1. Требования к системе
- Микросервисная архитектура (каждый агент — отдельный сервис).
- REST API для взаимодействия агентов с очередью.
- Хранение данных: PostgreSQL для задач и логов, Redis для временных блокировок.
- Масштабируемость: возможность добавления новых агентов без остановки системы.

### 2. Ключевые компоненты
| Компонент        | Функция                                                                 |
|------------------|-------------------------------------------------------------------------|
| Task Queue       | Центральная очередь. Принимает задачи, назначает ID, хранит статус.    |
| Coordinator      | Управляет приоритетами, проверяет тайм-ауты, перераспределяет задачи.  |
| Agent (шаблон)   | Универсальный исполняющий модуль. Подписывается на очередь, отчитывается. |
| Logger / Auditor | Записывает все события, формирует метрики.                             |

### 3. Поток выполнения
1. Задача поступает в Task Queue с указанием приоритета и типа.
2. Coordinator проверяет, нет ли уже такой задачи (по хешу содержимого). Если дубликата нет — добавляет.
3. Свободный Agent получает задачу с наибольшим приоритетом.
4. Agent выполняет задачу, формирует отчёт, отправляет в Logger.
5. Coordinator отмечает задачу как выполненную, при необходимости запускает зависимые задачи.

### 4. Пример отчёта агента
```json
{
  "task_id": "abc-123",
  "agent_id": "agent-04",
  "status": "success",
  "result": "Файл обработан, создана резервная копия.",
  "duration_ms": 4523,
  "timestamp": "2025-03-24T10:15:30Z"
}
```

### 5. Правила для агентов
- Не брать задачу, если её ID уже есть в списке «в работе» у другого агента (проверка через блокировку Redis).
- При сбое отправлять отчёт со статусом «error» и кодом ошибки.
- Если задача не выполнена за тайм-аут (задаётся в задаче) — Coordinator переводит её обратно в очередь.

## Дорожная карта (MVP → релиз)

1. **Неделя 1–2**: Разработка базового Task Queue и Coordinator (REST API, PostgreSQL).  
2. **Неделя 3**: Прототип одного Agent с чтением из очереди и отправкой отчёта.  
3. **Неделя 4**: Интеграция Logger, тестирование сценариев с 3 агентами.  
4. **Неделя 5**: Оптимизация приоритетов, добавление веб-интерфейса мониторинга.  
5. **Неделя 6**: Нагрузочное тестирование, документирование, подготовка к продакшену.

## Критерии успеха
- Время от постановки задачи до завершения не превышает 5 секунд для 100 одновременных задач.
- Ни одна задача не теряется при отказе одного агента (перераспределение).
- Все отчёты сохраняются, дублирование задач исключено.
